term query → Exact match (NO analysis)
==========
    Used on:
        keyword
        numbers
        booleans
        IDs
            {
              "term": {
                "status.keyword": "FAILED"
              }
            }

    ✔ Exact value
    ✔ Case-sensitive (usually)
    ❌ No tokenization
    📌 Use when value must match exactly.

match query → Full-text search (ANALYZED)
===========
    Used on: text fields
           {
              "match": {
                "message": "database error"
              }
            }
    What ES really searches: ["database", "error"]

    ✔ Order doesn’t matter
    ✔ Words can appear anywhere
    ✔ Scoring applies

match_phrase → Exact phrase in order
===========
    Used on:  text fields
    {
      "match_phrase": {
        "message": "database error"
      }
    }
    Matches:
    ✔ "database error occurred"
    ❌ "error in database"

    Order matters. Tokens must be adjacent (unless slop is used).

Range Query
===========
    Used for:
        numbers
        dates
        timestamps
            {
              "range": {
                "@timestamp": {
                  "gte": "now-1h",
                  "lte": "now"
                }
              }
            }
    Other operators:
    gt → greater than
    gte → greater than or equal
    lt → less than
    lte → less than or equal
    📌 Always used in filter context unless it affects scoring (rare).

Exists Query
    Find documents where a field is present.
        {
          "exists": {
            "field": "error_code"
          }
        }
    Matches if:
        field exists in _source
        not null
        not empty array
    Great for:
        data quality checks
        “missing field” debugging

4️⃣ Price
Example:
1999.99
You want to:
filter price ranges
average price aggregation
👉 Mapping?

PUT /prices
{
    "mapping":{
        "properties":{
            "price":{
                "type": "scaled_float"
            }
        }
    }
}

💡 Why use scaled_float?
    1️⃣ Better performance 🚀
    Integer operations are faster than floating-point operations
    Less CPU overhead during aggregations
    2️⃣ Less storage 🧱
    Uses doc_values (columnar storage) efficiently
    Takes less disk space than float/double
    3️⃣ Predictable precision 🎯
    No floating-point rounding surprises
    You control precision via scaling_factor

🎯 When SHOULD you use it?
    Perfect for:
    💰 Prices (e.g., £19.99)
    ⭐ Ratings (e.g., 4.5)
    📊 Percentages (e.g., 87.25%)
❌ When NOT to use it?
    Avoid when:
        You need very high precision (scientific calculations)
        Values vary wildly in decimal places
