1️⃣ lowercase filter
    🧠 What it does
        Converts all tokens to lowercase.
        That’s it. But it’s critical.
        Search is usually case-insensitive.
        Without this filter, "Error" and "error" are different tokens.

        Example:
            Request:
                POST /_analyze
                {
                    "tokenizer": {
                      "type": "pattern",
                      "pattern": "[.]"
                    },
                    "text": "Renjith. Ravindranatha Panikar",
                    "filter":["lowercase"]
                }
            Reponse:
                {
                  "tokens": [
                    {
                      "token": "renjith",
                      "start_offset": 0,
                      "end_offset": 7,
                      "type": "word",
                      "position": 0
                    },
                    {
                      "token": " ravindranatha panikar",
                      "start_offset": 8,
                      "end_offset": 30,
                      "type": "word",
                      "position": 1
                    }
                  ]
                }

2️⃣ asciifolding filter
    🧠 What it does
        Converts accented / Unicode characters → plain ASCII equivalents.
            é → e
            ö → o
            ñ → n
            ç → c

        So searches work even if users don’t type accents.
        Example:
            Request:
                POST /_analyze
                {
                    "tokenizer": "keyword",
                    "text": "Café Coffeday",
                    "filter":["asciifolding"]
                }
            Response:
                {
                  "tokens": [
                    {
                      "token": "Cafe Coffeday",
                      "start_offset": 0,
                      "end_offset": 13,
                      "type": "word",
                      "position": 0
                    }
                  ]
                }

3️⃣ stop filter
    🧠 What it does
        Removes very common words that usually don’t add meaning.

    Examples:
        the, is, a, an, of, to, in, and

    Example:
        Request:
            POST /_analyze
            {
                "tokenizer": "standard",
                "text": "ElasticSearch is good",
                "filter":["stop", "lowercase"]
            }
        Response:
            {
              "tokens": [
                {
                  "token": "elasticsearch",
                  "start_offset": 0,
                  "end_offset": 13,
                  "type": "<ALPHANUM>",
                  "position": 0
                },
                {
                  "token": "good",
                  "start_offset": 17,
                  "end_offset": 21,
                  "type": "<ALPHANUM>",
                  "position": 2
                }
              ]
            }

        As you can see the "lowercase" is applied before the "stop" filter, so "is" becomes "is" and then is removed by the stop filter.

        Custom stop words:
            Request:
                POST /_analyze
                {
                  "tokenizer": "whitespace",
                  "text": "The Predaor, is a movie",
                  "filter": [
                    {
                      "type": "stop",
                      "stopwords": [
                        "is",
                        "a"
                      ]
                    }
                  ]
                }

            Response:
                {
                  "tokens": [
                    {
                      "token": "The",
                      "start_offset": 0,
                      "end_offset": 3,
                      "type": "<ALPHANUM>",
                      "position": 0
                    },
                    {
                      "token": "Predaor,",
                      "start_offset": 4,
                      "end_offset": 13,
                      "type": "<ALPHANUM>",
                      "position": 1
                    },
                    {
                      "token": "movie",
                      "start_offset": 22,
                      "end_offset": 27,
                      "type": "<ALPHANUM>",
                      "position": 4
                    }
                  ]
                }

4️⃣ stemmer filter
    This is where search starts becoming meaning-based, not word-based.

    🧠 What a stemmer does
        Reduces words to their root form.

        run
        running
        runs
        runner

        All become:
            run

        So searching run matches documents with running.

    Example:
        Request:
            POST /_analyze
            {
                "tokenizer": "standard",
                "text": "Renjith running",
                "filter":["stemmer"]
            }

        Response:
            {
              "tokens": [
                {
                  "token": "renjith",
                  "start_offset": 0,
                  "end_offset": 7,
                  "type": "<ALPHANUM>",
                  "position": 0
                },
                {
                  "token": "run",
                  "start_offset": 8,
                  "end_offset": 15,
                  "type": "<ALPHANUM>",
                  "position": 1
                }
              ]
            }

        Example 2:
            Request:
                POST /_analyze
                {
                  "tokenizer": "standard",
                  "text": "Renjith running",
                  "filter": [
                    "lowercase",
                    {
                      "type": "stemmer",
                      "language": "english"
                    }
                  ]
                }
            Response:
                {
                  "tokens": [
                    {
                      "token": "renjith",
                      "start_offset": 0,
                      "end_offset": 7,
                      "type": "<ALPHANUM>",
                      "position": 0
                    },
                    {
                      "token": "run",
                      "start_offset": 8,
                      "end_offset": 15,
                      "type": "<ALPHANUM>",
                      "position": 1
                    }
                  ]
                }

5️⃣ synonym filter

    If configured well → search feels smart
    If configured badly → search becomes unpredictable


    🧠 What synonyms do
        They make different words behave as the same.
        Example:

            laptop = notebook
            movie = film
            error = failure

        So searching film finds documents with movie.

    Example:
        Request:
            POST /_analyze
            {
              "tokenizer": "standard",
              "filter":[
                "lowercase",
                {
                  "type": "synonym",
                  "synonyms": [
                    "film, movie, cinema, picture",
                    "good, nice, interesting"
                  ]
                }
              ],
              "text": "movie was Good"
            }
        Response:
            {
              "tokens": [
                {
                  "token": "movie",
                  "start_offset": 0,
                  "end_offset": 5,
                  "type": "<ALPHANUM>",
                  "position": 0
                },
                {
                  "token": "film",
                  "start_offset": 0,
                  "end_offset": 5,
                  "type": "SYNONYM",
                  "position": 0
                },
                {
                  "token": "cinema",
                  "start_offset": 0,
                  "end_offset": 5,
                  "type": "SYNONYM",
                  "position": 0
                },
                {
                  "token": "picture",
                  "start_offset": 0,
                  "end_offset": 5,
                  "type": "SYNONYM",
                  "position": 0
                },
                {
                  "token": "was",
                  "start_offset": 6,
                  "end_offset": 9,
                  "type": "<ALPHANUM>",
                  "position": 1
                },
                {
                  "token": "good",
                  "start_offset": 10,
                  "end_offset": 14,
                  "type": "<ALPHANUM>",
                  "position": 2
                },
                {
                  "token": "nice",
                  "start_offset": 10,
                  "end_offset": 14,
                  "type": "SYNONYM",
                  "position": 2
                },
                {
                  "token": "interesting",
                  "start_offset": 10,
                  "end_offset": 14,
                  "type": "SYNONYM",
                  "position": 2
                }
              ]
            }

    Index-time vs Query-time synonyms

        ❌ Index-time synonyms

            Synonyms applied when indexing.
            Problems:
                Index becomes bigger
                Hard to change later
                Requires reindex
                Can mess up scoring

        ✅ Query-time synonyms (best practice)

            Synonyms applied only during search.
            Benefits:
                Flexible
                Change anytime
                No reindex needed
                Cleaner index

            Use synonyms at query-time unless you have a strong reason not to.

    🧠 Order matters!

        Correct order:
            → lowercase
            → asciifolding
            → stop
            → stemmer
            → synonyms

        Why?
        Synonyms must match processed tokens.


    🧠 synonym vs synonym_graph (multi-word synonyms)

        For single words (laptop = notebook) both filters behave the same.
        The difference appears with MULTI-WORD synonyms:

            ny = new york

        Search for "ny" should match:
            docs containing "ny"
            docs containing "new york" (both words together)

        ❌ synonym (flat)
            Output is a flat list of tokens.
            It does not record that "ny" is a complete alternative to "new york".
            Query becomes:  (ny or new) AND york
            A doc that only has "ny" is MISSED.

        ✅ synonym_graph
            Output is a token graph (alternative paths).
            Query becomes:  ny OR (new AND york)
            Both kinds of docs are found.

        Rule:
            Search time  → synonym_graph
            Index time   → synonym (Lucene cannot index a graph; or use synonym_graph + flatten_graph)

        Setup:
            PUT synm_test
            {
              "settings": {
                "analysis": {
                  "filter": {
                    "syn_flat": {
                      "type": "synonym",
                      "synonyms": ["ny, new york"]
                    },
                    "syn_graph": {
                      "type": "synonym_graph",
                      "synonyms": ["ny, new york"]
                    }
                  },
                  "analyzer": {
                    "analyser_flat": {
                      "tokenizer": "standard",
                      "filter": ["syn_flat"]
                    },
                    "analyser_graph": {
                      "tokenizer": "standard",
                      "filter": ["syn_graph"]
                    }
                  }
                }
              },
              "mappings": {
                "properties": {
                  "data": { "type": "text" }
                }
              }
            }

            POST synm_test/_bulk
            {"index": {"_id": 1}}
            {"data": "best pizza in ny"}
            {"index": {"_id": 2}}
            {"data": "visit new york city"}

        Note: documents are indexed with the standard analyzer only.
        The synonym analyzers are applied at query time (analyzer override in the query).

        Step 1: analyze "ny" with the flat analyzer
            Request:
                POST synm_test/_analyze
                {
                    "text": "ny",
                    "analyzer": "analyser_flat"
                }
            Response:
                {
                  "tokens": [
                    {
                      "token": "ny",
                      "start_offset": 0,
                      "end_offset": 2,
                      "type": "<ALPHANUM>",
                      "position": 0
                    },
                    {
                      "token": "new",
                      "start_offset": 0,
                      "end_offset": 2,
                      "type": "SYNONYM",
                      "position": 0
                    },
                    {
                      "token": "york",
                      "start_offset": 0,
                      "end_offset": 2,
                      "type": "SYNONYM",
                      "position": 1
                    }
                  ]
                }

        Step 2: analyze "ny" with the graph analyzer
            Request:
                POST synm_test/_analyze
                {
                    "text": "ny",
                    "analyzer": "analyser_graph"
                }
            Response:
                {
                  "tokens": [
                    {
                      "token": "new",
                      "start_offset": 0,
                      "end_offset": 2,
                      "type": "SYNONYM",
                      "position": 0
                    },
                    {
                      "token": "ny",
                      "start_offset": 0,
                      "end_offset": 2,
                      "type": "<ALPHANUM>",
                      "position": 0,
                      "positionLength": 2
                    },
                    {
                      "token": "york",
                      "start_offset": 0,
                      "end_offset": 2,
                      "type": "SYNONYM",
                      "position": 1
                    }
                  ]
                }

        🧠 Why positionLength is important

            Same 3 tokens, same positions. The ONLY difference is one line:
                "positionLength": 2   (on "ny")

            positionLength = how many positions a token covers.
            Default is 1.

            Here "ny" covers positions 0 and 1 → the same span as "new" + "york".
            That tells Elasticsearch there are 2 alternative paths:

                path A:  ny
                path B:  new → york

            Without positionLength (flat):
                "ny" is assumed to cover only position 0.
                Elasticsearch sees: position 0 = (ny or new), position 1 = york
                "ny" is no longer a complete alternative, so a query built from
                this stream needs "york" as well.

            With positionLength (graph):
                Elasticsearch builds one query per path:  ny OR (new AND york)

            Also matters for phrase queries:
                the span decides which tokens must sit next to each other.

        Step 3: search "ny" with operator "and" (flat)
            Request:
                POST synm_test/_search
                {
                    "query": {
                        "match": {
                          "data": {"query": "ny", "analyzer": "analyser_flat", "operator": "and"}
                        }
                    }
                }
            Response (trimmed):
                total hits: 1
                    _id 2  "visit new york city"   _score 1.3862942

            Doc 1 "best pizza in ny" is MISSED.
            Query was (ny or new) AND york, and doc 1 has no "york".

        Step 4: search "ny" with operator "and" (graph)
            Request:
                POST synm_test/_search
                {
                    "query": {
                        "match": {
                          "data": {"query": "ny", "analyzer": "analyser_graph", "operator": "and"}
                        }
                    }
                }
            Response (trimmed):
                total hits: 2
                    _id 2  "visit new york city"   _score 1.3862942
                    _id 1  "best pizza in ny"      _score 0.6931471

            Both docs found.
            Doc 2 ranks higher: it matches two terms (new, york). Doc 1 matches one (ny).

        🧠 Why operator "and" is needed in this test

            operator decides how the query tokens are combined:
                or  (default) → doc matches if ANY token is present
                and           → doc must contain ALL tokens of a path

            With the default "or", the flat query is: ny OR new OR york.
            Doc 1 still matches on "ny" alone, so flat and graph look the same
            and the problem is hidden.
            "and" (or match_phrase) forces Elasticsearch to respect how the
            tokens are grouped. That is where flat breaks.

        🧠 Debugging lesson from this exercise

            A query on a field that does not exist returns 0 hits and NO error.
            If a search returns nothing:
                1. match_all → do the docs exist?
                2. compare the field name in the query with _source / _mapping
                3. only then look at analyzers
